C'est ce qui rend Nuclei si puissant, les vérifications sont très simples à écrire et de multiples vérifications peuvent être ajoutées selon les besoins pour un balayage très efficace. Types ### Plusieurs comparateurs peuvent être spécifiés dans une requête. Il y a fondamentalement 7 types de matchers : ```` Matcher Type Part Matched status Integer Comparisons of Part size Content Length of Part word Part for a protocol regex Part for a protocol binary Part for a protocol dsl Part for a protocol xpath Part for a protocol ```` Pour faire correspondre les codes d'état des réponses, vous pouvez utiliser la syntaxe suivante. ```` matchers : # Match the status codes - type : status # Some status codes we want to match status : - 200 - 302 ``` Pour faire correspondre des réponses binaires à des réponses hexadécimales, vous pouvez utiliser la syntaxe suivante : ``` matchers : - type : status # ``` matchers : - type : status # ```. ```` matchers : - type : binary binary : - \"504B0304\" # archive zip - \N- "526172211A070100\N" # archive RAR version 5.0 - \N- "FD377A585A0000\N" # xz tar.xz archive condition : or part : body ```Les outils de recherche supportent également les données encodées en hexadécimal qui seront décodées et comparées. ```` matchers : - type : word encoding : hex words : - \N "50494e47\N" part : body ```Les outils de recherche de mots et d'expressions rationnelles peuvent être configurés en fonction des besoins de l'utilisateur. Les analyseurs XPath utilisent des requêtes XPath pour faire correspondre les réponses XML et HTML. Si la requête XPath renvoie des résultats, elle est considérée comme une correspondance. ````Matchers : - type : xpath part : body xpath : - \N- "/html/head/title[contains(text(), \N'Example Domain\N)]\N" ````Les comparateurs complexes de type dsl permettent de construire des expressions plus élaborées à l'aide de fonctions d'aide. Ces fonctions permettent d'accéder à la réponse du protocole qui contient une variété de données basées sur chaque protocole. Consultez la documentation spécifique au protocole pour en savoir plus sur les différents résultats renvoyés. ```` matchers : - type : dsl dsl : - \"len(body)<1024 && status_code==200\" # Longueur du corps inférieure à 1024 et code d'état 200 - \"contains(toupper(body), md5(cookie))\" # Vérifie si la somme MD5 des cookies est contenue dans le corps en majuscules ```Chaque partie d'une réponse au protocole peut être traitée par un analyseur DSL. Voici quelques exemples : Réponse Partie Description Exemple : content_length En-tête Content-Length content_length >= 1024 status_code Code d'état de la réponse status_code==200 all_headers Tous les en-têtes len(all_headers) body Corps en tant que chaîne len(body) header_name Nom de l'en-tête avec - converti en _ len(user_agent) raw En-têtes + Réponse len(raw) ### Conditions Plusieurs mots et regex peuvent être spécifiés dans un seul matcher et peuvent être configurés avec différentes conditions telles que AND et OR. AND - L'utilisation de conditions AND permet de faire correspondre tous les mots de la liste de mots pour l'analyseur. Ce n'est que lorsque tous les mots auront été trouvés que la requête sera marquée comme réussie. OU - L'utilisation de conditions OU permet de faire correspondre un seul mot de la liste de l'outil de recherche. La demande sera considérée comme réussie si l'un des mots de la liste a été trouvé. Parties couvertes Plusieurs parties de la réponse peuvent également être couvertes par la requête. La partie couverte par défaut est le corps de la réponse si elle n'est pas définie. Exemple de correspondance pour le corps de la réponse HTTP en utilisant la condition AND : ```` matchers : # Correspondre au mot du corps - type : word # Quelques mots que nous voulons faire correspondre aux mots : - \N-[core]\N-[core]\N-[core]\N-[core]\N]" - \N-[config]\N-[config]\N-[config]\N-[config]\N-[config] # Les deux mots doivent être trouvés dans le corps de la réponse condition : and # Nous voulons faire correspondre le corps de la demande (par défaut) partie : body ``` De même, les matchers peuvent être écrits pour faire correspondre tout ce que vous voulez trouver dans le corps de la réponse, ce qui permet une créativité et une extensibilité illimitées. ### Tous les types de matchers supportent également les conditions négatives, particulièrement utiles lorsque vous recherchez une correspondance avec une exclusion. Ceci peut être utilisé en ajoutant negative : true dans le bloc de correspondance. Voici un exemple de syntaxe utilisant une condition négative, qui retournera toutes les URLs n'ayant pas PHPSESSID dans l'en-tête de réponse. ```` matchers : - type : word words : - \"PHPSESSID\" part : header negative : true ``` ### Multiple Matchers Plusieurs matchers peuvent être utilisés dans un seul modèle pour identifier plusieurs conditions avec une seule requête. Voici un exemple de syntaxe pour de multiples matchers. ```` matchers : - type : word name : php words : - \"X-Powered-By : PHP" - \N "PHPSESSID\N" part : header - type : mot nom : node mots : - \N "Server : NodeJS" - \N- "X-Powered-By : nodejs\N" condition : ou partie : en-tête - type : mot nom : python mots : - \N- "Python/2.\N" - \N- "Python/3.\N" condition : ou partie : en-tête ``` ### Matchers Condition Lors de l'utilisation de plusieurs matchers, la condition par défaut est de suivre l'opération OR entre tous les matchers, l'opération AND peut être utilisée pour s'assurer que le résultat est retourné si tous les matchers renvoient un résultat vrai. ```` matchers-condition : and matchers : - type : word words : - \"X-Powered-By : PHP" - \N- "PHPSESSID\N" condition : ou partie : en-tête - type : mot mots : - \N "PHP" part : body ``` # Extractors Review details on extractors for Nuclei Les extracteurs peuvent être utilisés pour extraire et afficher dans les résultats une correspondance à partir de la réponse renvoyée par un module. ### Plusieurs extracteurs peuvent être spécifiés dans une requête. Pour l'instant, nous supportons cinq types d'extracteurs. ``` regex - Extrait les données de la réponse en se basant sur une expression régulière. kval - Extrait les données formatées key : value/key=value de l'en-tête de la réponse/Cookie json - Extrait les données de la réponse basée sur JSON dans une syntaxe similaire à JQ. xpath - Extrait les données basées sur xpath de la réponse HTML dsl - Extrait les données de la réponse en se basant sur une expression DSL. ```` Regex Extractor Exemple d'extracteur pour le corps de la réponse HTTP en utilisant des regex : ```` extractors : - type : regex # type de l'extracteur part : body # partie de la réponse (header,body,all) regex : - \"(A3T[A-Z0-9]|AKIA|AGPA|AROA|AIPA|ANPA|ANVA|ASIA)[A-Z0-9]{16}\" # regex à utiliser pour l'extraction. ```` Kval Extractor Un exemple d'extracteur kval pour extraire l'en-tête content-type de la réponse HTTP. ```` extractors : - type : kval # type de l'extracteur kval : - content_type # valeur de l'en-tête/cookie à extraire de la réponse ```` Notez que content-type a été remplacé par content_type car l'extracteur kval n'accepte pas le tiret (-) en entrée et doit être remplacé par un trait de soulignement (_). Extracteur JSON Un exemple d'extracteur json pour extraire la valeur de l'objet id d'un bloc JSON. ``` - type : json # type de l'extracteur part : body name : user json : - \'.[] | .id\' # syntaxe JQ pour l'extraction ``` Pour plus de détails sur JQ - https://github.com/stedolan/jq Xpath Extractor Un exemple d'extracteur xpath pour extraire la valeur de l'attribut href de la réponse HTML. ``` Extracteurs : - type : xpath # type de l'extracteur attribut : href # valeur de l'attribut à extraire (optionnel) xpath : - \'/html/body/div/p[2]/a\' # valeur xpath pour l'extraction ```` Avec un simple copier-coller dans le navigateur, nous pouvons obtenir la valeur xpath de n'importe quel contenu de page web. DSL Extractor Un exemple d'extracteur dsl pour extraire la longueur effective du corps grâce à la fonction d'aide len de la réponse HTTP. ``` Extracteurs : - type : dsl # type de l'extracteur dsl : - len(body) # valeur de l'expression dsl à extraire de la réponse ```` Dynamic Extractor Les extracteurs peuvent être utilisés pour capturer des valeurs dynamiques au moment de l'exécution lors de l'écriture de modèles multi-requêtes. Les jetons CSRF, les en-têtes de session, etc. peuvent être extraits et utilisés dans les requêtes. Cette fonctionnalité n'est disponible qu'au format RAW. Exemple de définition d'un extracteur dynamique avec name api qui capturera un motif basé sur une expression rationnelle à partir de la requête. ``` Extracteurs : - type : regex name : api part : body internal : true # Requis pour l'utilisation de variables dynamiques regex : - \"(?m)[0-9]{3,10}\.[0-9]+\" ``` La valeur extraite est stockée dans la variable api, qui peut être utilisée dans n'importe quelle section des requêtes suivantes. Des variables dynamiques peuvent être placées dans le chemin pour modifier son comportement à l'exécution. Les variables commencent par {{ et se terminent par }} et sont sensibles à la casse. {{BaseURL}} - Cette variable remplacera l'URL d'entrée spécifiée dans le fichier cible lors de l'exécution de la requête. {{RootURL}} - Ceci remplacera, lors de l'exécution de la requête, l'URL racine telle que spécifiée dans le fichier cible. {{Hostname}} - La variable Hostname est remplacée par le nom d'hôte et le port de la cible au moment de l'exécution. {{Host}} - Ceci remplacera à l'exécution la requête par l'hôte d'entrée tel que spécifié dans le fichier cible. {{Port}} - Ceci remplacera à l'exécution la demande par le port d'entrée tel que spécifié dans le fichier cible. {{Path}} - Ceci remplacera lors de l'exécution de la demande par le chemin d'entrée tel que spécifié dans le fichier cible. {{Fichier}} - Ceci remplacera lors de l'exécution de la demande par le nom du fichier d'entrée tel que spécifié dans le fichier cible. {{Scheme}} - Ceci remplacera lors de l'exécution de la requête par le schéma du protocole tel que spécifié dans le fichier cible. Type batteringram pitchfork clusterbomb Support ✔ ✔ ✔ batteringram Le type d'attaque batteringram place la même valeur de charge utile dans toutes les positions. Il n'utilise qu'un seul ensemble de charges utiles. Il parcourt en boucle l'ensemble de charges utiles et remplace toutes les positions par la valeur de la charge utile. fourche Le type d'attaque fourche utilise un ensemble de charges utiles pour chaque position. Il place la première charge utile en première position, la deuxième charge utile en deuxième position, et ainsi de suite. Il parcourt ensuite en boucle tous les jeux de données utiles en même temps. La première requête utilise la première charge utile de chaque jeu, la deuxième requête utilise la deuxième charge utile de chaque jeu, et ainsi de suite. clusterbomb L'attaque cluster bomb tente toutes les combinaisons possibles de charges utiles. Elle place toujours la première charge utile en première position et la deuxième charge utile en deuxième position. Mais lorsqu'elle parcourt les ensembles de charges utiles, elle essaie toutes les combinaisons. Il parcourt ensuite tous les ensembles de données utiles en même temps. La première demande utilise la première charge utile de chaque ensemble, la deuxième demande utilise la deuxième charge utile de chaque ensemble, et ainsi de suite. Ce type d'attaque est utile pour une attaque par force brute. Chargez une liste de noms d'utilisateur couramment utilisés dans le premier ensemble de données utiles et une liste de mots de passe couramment utilisés dans le deuxième ensemble de données utiles. L'attaque par bombes à fragmentation essaiera alors toutes les combinaisons. Auparavant, si vous vouliez écrire un modèle de réseau pour un exploit ciblant SSH, vous deviez spécifier à la fois le nom d'hôte et le port dans le champ hôte, comme ceci : ``` host : - \N- "{{Nom d'hôte}}" - \N- "{{Hôte}}:22\N" ``` Dans l'exemple ci-dessus, deux requêtes réseau sont envoyées : une vers le port spécifié dans l'entrée/cible, et une autre vers le port SSH par défaut (22). La raison de l'introduction du champ port est de fournir aux utilisateurs plus de flexibilité lors de l'exécution de modèles réseau sur les ports par défaut et non par défaut. Si l'utilisateur ne spécifie aucun port en entrée, le port 22 sera utilisé par défaut. Cependant, cette approche peut ne pas être simple à comprendre et peut générer des avertissements dans les journaux puisqu'une requête est censée échouer. Un autre problème lié à la conception précédente de l'écriture des modèles de réseau est que les requêtes peuvent être envoyées à des ports inattendus. Par exemple, si un service web fonctionne sur le port 8443 et que l'utilisateur exécute : $ nuclei -u scanme.sh:8443 Dans ce cas, le modèle xyz-ssh-exploit enverra une requête à scanme.sh:22 et une autre requête à scanme.sh:8443, ce qui peut renvoyer des réponses inattendues et éventuellement entraîner des erreurs. Ceci est particulièrement problématique dans les scénarios d'automatisation.
